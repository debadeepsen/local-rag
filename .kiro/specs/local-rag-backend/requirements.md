# Requirements Document

## Introduction

This document describes the requirements for a Local RAG (Retrieval-Augmented Generation) Backend system. The system is a FastAPI-based backend that serves as a RAG orchestrator, enabling users to ask questions about local documents and receive answers grounded in those documents with source citations.

The system ingests documents (PDFs, text files) from a local folder, chunks text into manageable pieces, creates embeddings using Ollama's nomic-embed-text model, stores vectors in ChromaDB (local embedded mode), and answers user questions by retrieving relevant document chunks and building prompts for the LLM.

### Key Goals

- Provide a local, offline-capable RAG system
- Support common document formats (PDF, text)
- Return answers with source citations
- Run entirely on local hardware (Ollama, ChromaDB)
- Provide a clean HTTP API for integration

## Glossary

- **System**: The Local RAG Backend system
- **Document**: A PDF or text file stored in the data/raw-docs folder
- **Chunk**: A segment of text extracted from a document, typically 500 characters with 50-character overlap
- **Embedding**: A numerical vector representation of text generated by Ollama's nomic-embed-text model
- **ChromaDB**: The local vector database storing embeddings and document metadata
- **LLM**: The large language model (qwen3:8b) running on Ollama
- **User**: An external system or human interacting with the System via HTTP API
- **Question**: A natural language query submitted by a User to the System

## User Roles and Personas

- **End User**: A person who submits questions about local documents and receives answers with citations
- **System Administrator**: A person who manages the system, adds documents to the ingestion folder, and monitors system health

## Requirements

### Requirement 1: Health Check Endpoint

**User Story:** As a system administrator, I want to verify the System is running, so that I can confirm service availability.

#### Acceptance Criteria

1. WHEN a GET request is made to the / endpoint, THE System SHALL return a JSON response with a "message" field containing "RAG API running"
2. IF the System is operational, THEN the response status code SHALL be 200

### Requirement 2: Document Ingestion Endpoint

**User Story:** As a system administrator, I want to trigger document ingestion from a local folder, so that new documents become searchable.

#### Acceptance Criteria

1. WHEN a POST request is made to the /ingest endpoint, THE System SHALL scan the data/raw-docs folder for PDF and text files
2. FOR EACH PDF file found, THE System SHALL extract text using a PDF parser
3. FOR EACH text file found, THE System SHALL read the file content directly
4. THE System SHALL chunk each document's text into segments of 500 characters with 50-character overlap
5. FOR EACH chunk, THE System SHALL generate an embedding using Ollama's nomic-embed-text model
6. THE System SHALL store each chunk and its embedding in ChromaDB with metadata including the source filename
7. IF an error occurs during ingestion of a specific file, THE System SHALL log the error and continue processing remaining files
8. THE System SHALL return a JSON response indicating the number of files processed and any errors encountered

### Requirement 3: Chat/Question-Answering Endpoint

**User Story:** As an end user, I want to submit a question and receive an answer with source citations, so that I can understand the context of the response.

#### Acceptance Criteria

1. WHEN a POST request with a valid JSON body containing a "question" field is made to the /chat endpoint, THE System SHALL process the request
2. THE System SHALL generate an embedding for the question using Ollama's nomic-embed-text model
3. THE System SHALL query ChromaDB for the 3 most relevant document chunks based on the question embedding
4. THE System SHALL build a prompt by combining the retrieved chunks as context with the original question
5. THE System SHALL send the prompt to Ollama's qwen3:8b model and receive a response
6. THE System SHALL return a JSON response containing the answer and an array of source citations
7. EACH source citation SHALL include the chunk text and the source filename from ChromaDB metadata
8. IF the question is empty or missing, THE System SHALL return a 400 status code with an error message
9. IF Ollama is unavailable, THE System SHALL return a 503 status code with an error message
10. IF ChromaDB is unavailable, THE System SHALL return a 503 status code with an error message

### Requirement 4: Source Citation Format

**User Story:** As an end user, I want to see which parts of the documents the answer is based on, so that I can verify the response and reference the original material.

#### Acceptance Criteria

1. EACH source citation in the /chat response SHALL include the "text" field containing the retrieved chunk
2. EACH source citation SHALL include the "source" field containing the filename from ChromaDB metadata
3. THE System SHALL preserve the original text of each chunk without modification

## Non-Functional Requirements

### Requirement 5: Performance

**User Story:** As an end user, I want reasonably fast responses, so that the system is usable for interactive queries.

#### Acceptance Criteria

1. FOR questions requiring retrieval of 3 chunks, THE System SHALL return a response within 30 seconds
2. FOR document ingestion of a single 10-page PDF, THE System SHALL complete within 60 seconds
3. THE System SHALL handle concurrent requests with a minimum of 5 requests per second

### Requirement 6: Reliability

**User Story:** As a system administrator, I want the system to handle failures gracefully, so that partial failures don't affect overall operation.

#### Acceptance Criteria

1. IF a document fails to parse during ingestion, THE System SHALL log the error and continue with other documents
2. IF Ollama is temporarily unavailable during question answering, THE System SHALL return a 503 status code with a descriptive error message
3. IF ChromaDB is temporarily unavailable, THE System SHALL return a 503 status code with a descriptive error message
4. THE System SHALL maintain data integrity in ChromaDB even if ingestion is interrupted

### Requirement 7: Data Persistence

**User Story:** As a system administrator, I want embeddings and documents to persist across system restarts, so that I don't need to re-ingest documents after each restart.

#### Acceptance Criteria

1. ChromaDB SHALL store data in the data/chroma folder using persistent storage
2. WHEN the System is restarted, ALL previously ingested documents SHALL remain in ChromaDB
3. WHEN new documents are added to data/raw-docs, THE System SHALL be able to ingest them without re-ingesting existing documents

### Requirement 8: Local Operation

**User Story:** As a user, I want the system to run entirely locally without internet access, so that I can use it in air-gapped environments.

#### Acceptance Criteria

1. ALL model inference (embeddings and LLM) SHALL use Ollama running locally on port 11434
2. ALL vector storage SHALL use ChromaDB in embedded mode on local disk
3. The System SHALL NOT require external API keys or cloud services to operate
4. The System SHALL function after initial model downloads are complete

### Requirement 9: API Usability

**User Story:** As a developer integrating with the System, I want clear API responses, so that I can build client applications easily.

#### Acceptance Criteria

1. ALL error responses SHALL include a "error" or "message" field describing the issue
2. ALL successful responses SHALL use standard HTTP status codes (200, 201, etc.)
3. THE /chat response structure SHALL be consistent: {"answer": string, "sources": array}
4. EACH source in the sources array SHALL have a consistent structure: {"text": string, "source": string}

## Acceptance Criteria Summary

| Feature | Endpoint | Key Acceptance Criteria |
|---------|----------|------------------------|
| Health Check | GET / | Returns 200 with status message |
| Document Ingestion | POST /ingest | Scans folder, chunks text, creates embeddings, stores in ChromaDB |
| Question Answering | POST /chat | Retrieves chunks, builds prompt, generates answer, returns sources |
| Source Citations | /chat response | Each source includes text and filename |
| Performance | All endpoints | Responses within defined time limits |
| Reliability | All endpoints | Graceful error handling with appropriate status codes |
| Persistence | ChromaDB | Data survives system restarts |
| Local Operation | All components | No external dependencies after setup |
